### Domain and workflow invariants retained

`domain.ts` defines company facts, application/screening, administrative requirements, versioned evidence, company-owned qualifications, WorkItems, workflow instances, accepted events, integration attempts and outbox. Company remains the business identity, including one-person companies. These are interfaces and explicit policies, not fully isolated DDD aggregates/value-object classes; one snapshot transaction can update several related records.

`orchestration.ts` implements compiled CompanyOnboarding v2 / SkillQualification v2 transitions and accepted-event correlation/duplicate/expected-work checks. `companyLifecycle.ts` derives current readiness and operational effects independently of historically completed onboarding. `migration.ts` retains business schema 2/3-to-4 upgrades for local old snapshots. No business handlers, workflow definitions, readiness rules or business event payloads changed in this iteration.

Business action -> existing service use case -> exclusive lock/latest state -> domain facts -> typed event envelope -> `LocalOrchestrator.deliver` correlation and rule evaluation -> WorkItem completion/new participant work -> readiness/operational policy -> auxiliary trigger/capture projection -> atomic snapshot/revision -> revision-only notification -> next participant reloads authoritative work.

Ready = administrative approval AND portal setup AND confirmed initial training AND at least one approved skill. Eligible = Ready AND Active. Onboarding completion is historical. Initial activation publication remains explicit user-triggered internal automation in Monitor; Contractors cannot execute it. Last-approved-skill loss suspends an Active company. Later qualification approval can restore Ready but never clears Suspended. A completed CompanyOnboarding instance never receives new work or resumes.

Workflows persist their waits, processed event IDs and history. Technical failures persist attempts without successful business events; retries are explicit commands. Reminders/escalations use explicit simulation-clock advancement. Reopening a tab loads saved work; it does not recreate a Temporal worker or automatically run integrations. There is no Temporal server, durable background timer or cross-browser distributed execution.

## 3. Recording semantics and decisions

`change` records the pre-command accepted event IDs. After the actual business command finishes, matching examines only newly accepted persisted events in their array order, inside the same lock/save. Existing history is not replayed on initialization, rule creation, refresh, save or restore. No React effect, polling timer or BroadcastChannel listener captures events. A triggering command that emits several events still has one committed state: each matching occurrence's Frame 0 projects that final snapshot, not invented intermediate states.

Deduplication uses accepted `eventId` + exact root workflow ID, the currently supported map scope. Equivalent enabled rules create one automatic recording and store every rule's ID/name/kind at firing time. Editing/removing a rule preserves that provenance. Each rule's count means accepted matching occurrences, including a failed start, rather than unique recordings across all rules. Initial Recruitment approval also legitimately emits SkillRequested; enabling that catalog entry catches initial qualifications as well as later requests.

Each running recording consumes scoped event/attempt/timer identities and appends at most one frame for a relevant commit with changed visual information. A second identical failed attempt can update seen identities without an identical extra frame. The root's legitimate terminal commit is captured before Completed; stopped/completed frames remain immutable. Viewing another journey or disabling/deleting its rule does not stop it.

A CompanyOnboarding recording includes only its root and explicitly application-linked initial skill. Separate skill roots do not ingest another same-company qualification's execution. Readiness origin resolution uses explicit company/application identity and requires one uniquely identified company root, since lifecycle events can be published outside its original correlation. A post-completion readiness event can start a Completed Frame 0 view of that historical root; it cannot publish activation or remove suspension.

Capture failure quarantines that recording with a visible gap, preserving old frames. Other recordings continue. Failed automatic creation leaves a visible trigger/workspace warning and accepted occurrence metadata; it is not silently backfilled later. No capture auto-resume/repair feature was introduced. A storage transaction/quota failure still rejects the whole snapshot write as before; auxiliary failure isolation is not a browser quota-recovery guarantee. Manually corrupted auxiliary topology can also prevent validated export; the importer deliberately does not accept damaged references/maps.

Viz version 2 retains legacy `activeRecordingId` only as a fresh-launch/default-view compatibility hint. It never chooses which recordings capture. Journey Map binds its current viewing selection locally; existing tabs do not jump to another tab's newly started manual capture. New manual starts may update the fresh-launch default; selecting history does not write shared state. Old archived captures remain Stopped; a legacy active root already terminal becomes Completed at its last recorded frame revision, with no added frame.

No automatic retention/discard limit, second independent queue or event broker was introduced. See [`docs/viz-recording.md`](viz-recording.md) for the contract and limitations.

## 4. Workspace, persistence and multi-tab behavior

Live store remains IndexedDB `fieldwork-onboarding`, database v1, store `state`, key `current`; application business schema remains 4. Lock: `fieldwork-onboarding:commands:v1`. Channel: `fieldwork-onboarding:changes:v1`, only `{type: "committed", revision}` after transaction completion and lock release. All recording updates and business facts share one save; notifications cannot execute transitions.

Save takes a consistent logical snapshot under the command lock, including all business collections, clock, triggers/counts/enabled state, running and archived recordings, map definitions, frame causes, lineage and seen identities. Sessions, tab preferences, browser internals and local replacement epoch are excluded. New format 2 files explicitly support Viz 2. Original format 1/Viz 1 files validate before a metadata-only upgrade; they do not require regeneration. Compatibility copies of all four original fictional files are committed under `tests/fixtures/workspace-v1/`, with hashes/provenance. The actual `docs/chet/` directory remains local-only.

Load previews and requires confirmation, offers a current-state backup, and replaces atomically. Revision becomes `max(local, incoming) + 1`; a fresh local epoch rejects queued old-workspace commands. Stale previews reject, transaction abort leaves all prior state intact, and all tabs refresh through existing invalidation/focus/visibility/pageshow handling. Imported history never fires triggers. Reset with typed RESET clears triggers, recordings and every business collection together.

For each healthy restored running recording, equal-valued JSON projection objects are aligned to canonical projection order; no recorded value/number/cause changes. This is independent of an unrelated trigger warning. Reordered-key tests include a real additional identical failed attempt: the new identity is consumed without inventing a visual frame. A removed contractor ID signs out; invalid internal company/queue selections require explicit choice rather than substitution. Existing valid sessions and Operations role preferences remain local and retained.

Stopped/completed captures are not projected but remain in every full-state clone/write/export. The existing import limit is 50 MiB; near-limit histories, browser quota exhaustion, long sessions and low-powered devices remain untested. No history is discarded silently.

## 7. Rules, assumptions, architecture choices and gaps

- **Implemented business rules:** separate historical completion/current readiness/operational state; explicit activation; Ready AND Active eligibility; approved company skill prerequisite; no completed-root resumption; loss of last approved skill suspends; regained qualifications do not unsuspend. No changes this iteration.
- **Provisional business assumptions:** two skill labels (HVAC/Plumbing), fictional evidence fixtures, fixed portal/training/vendor onboarding sequence, compiled initial approval process, company as identity, sample deadlines/reminder escalation. These remain prototype policies, not confirmed complete production requirements.
- **Architecture decisions this iteration:** closed opt-in trigger catalog; match newly accepted events in the existing atomic pipeline; independent recording status; original-file metadata migration; matched-rule snapshots survive rule edits/deletion; quarantine rather than fabricated recovery; legacy default-view field retained for backward compatibility. New origin captions are display metadata, not new workflow definitions.
- **Deviations/limits:** no unsupported workflow/map adapters or generic rules; no automatic capture retry/backfill; no business instrumentation was needed for the four requested points. No dependency for fonts; Windows uses local Bahnschrift variation, other systems use narrow sans-serif fallback and need visual acceptance. Source logo is unchanged.
- **Unresolved business decisions:** initial rejection/sole-skill invalidation recovery, suspension-removal administrative request/approval/audit, ongoing compliance/expiry/grace periods, company administrative changes after activation. Iteration 4 remains unimplemented.
- **Untested/manual:** actual OS save-picker UI; non-Windows fallback typography; Safari/Firefox; every-tab-closed processing (not supported); production service integration/auth; extreme history/quota/performance. Native HTML controls and retained keyboard/reduced-motion tests support accessibility, but this is not a formal accessibility audit.
- **Known defects:** none confirmed in final implemented acceptance paths after the recorded fixes. Technical limitations above remain explicit; manual product acceptance is outstanding.
